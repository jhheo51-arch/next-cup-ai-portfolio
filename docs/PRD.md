# NEXT CUP 제품 요구사항

## 1. 해결하려는 문제

좋아하던 음료가 없을 때, 같은 맛을 복원하는 대신 다음 잔에서도 필요한 특징을 확인하고 후보를 비교합니다.
본인은 이천 햅쌀 크림 프라푸치노의 구수함, 갈린 질감, 과자 같은 토핑과 출시 취지를 좋아했습니다. 이후 추천을 받아 딸기 딜라이트 요거트 블렌디드를 시도했고, 시원하게 갈린 음료를 좋아하며 맛도 괜찮았기 때문에 받아들였습니다.

이 경험은 한 사람의 회고입니다. 맛이 비슷해서 바꿨다는 근거도, 서비스가 선택을 개선했다는 근거도 아닙니다.

## 2. 사용자와 목표

- 대상 가설: 과거 또는 접근하기 어려운 메뉴에서 좋아했던 특징을 말로는 기억하지만 현재 후보로 연결하기 어려운 사람.
- 현재 제공 범위: 등록한 음료 5종에서 특징을 비교하는 개인용 시제품.
- 목표: 기억을 이번 선택의 조건으로 정리하고, 필수 조건에 맞는 후보가 없으면 보류한다.
- 제외: 전체 고객의 수요 규모 추정, 맛 재현, 지점 재고 조회, 건강상 안전 보장.

기억 입력 → 취향 확인 → 대안 또는 추천 보류 → 남은 요구 기록 → 동의 기반 후속 알림

## 3. AI를 사용하는 이유와 사용하지 않는 부분

| 선택한 방식 | 이유 | 한계 / 다른 선택 |
|---|---|---|
| 자유 문장을 AI가 특징으로 정리 | 과거와 현재, 좋아함과 피함, 허용과 필수를 구분해 입력 초안을 만듦 | 직접 고를 특징을 이미 아는 사람에게는 불필요할 수 있음 |
| 사람이 조건을 확인 | 인용이 원문에 있어도 의미가 잘못 연결될 수 있음 | 읽기와 수정 부담이 생김 |
| 코드가 최종 후보 검사 | 필수/비선호/자료 확인일을 반복 가능한 규칙으로 검사 | 등록 목록이 좁으면 후보가 없어짐 |
| AI 없이 직접 선택 가능 | 통신 장애와 AI를 원하지 않는 경우에도 목적 달성 | 자유 문장 해석은 제공하지 않음 |
| 남은 요구는 후속 기록 | 추천 실패의 원인을 검토할 단서 확보 | 건수를 신메뉴 수요나 구매 의사로 해석하지 않음 |

AI가 음료 이름이나 레시피를 창작하지 않습니다. 정해진 순서의 AI 보조 서비스이며 자율 주문 Agent가 아닙니다.

## 4. 기능과 수락 기준

| ID | 요구사항 | 확인할 동작 |
|---|---|---|
| F01 | 기억 입력과 전송 동의 | 최대 1,200자. 동의 없는 AI 전송 차단. 직접 선택은 동의 불필요 |
| F02 | 취향 해석 | 14개 특징 안에서 선호/비선호와 쌀 필수 여부를 추출. 원문 인용과 형식 검사 |
| F03 | 해석 확인 | AI 설명과 확인 질문 표시. 사용자가 태그와 필수 조건을 수정. 미확인 조건 임의 확정 금지 |
| F04 | 후보 비교 | 필수 조건 위반, 피하는 특징 포함, 오래된 자료 등 제외. 같은 맛이라고 안내하지 않음 |
| F05 | 추천 보류 | 후보 0개면 현재 목록의 한계를 안내. 조건을 자동 완화하지 않음 |
| F06 | 남은 요구 저장 | 비교 조건과 문장을 같은 브라우저에 저장. 새로고침 뒤 유지. 공개 게시나 회사 전송 없음 |
| F07 | 장애 처리 | 서버 해석 12초 제한. 입력 보존, 직접 선택, 늦은 응답 적용 차단. 503은 혼잡으로 구분 |
| F08 | 화면 | 가입 없음. 모바일과 데스크톱에서 주요 단계 사용 가능. 스크롤 이동은 유지 |
| F09 | CRM 운영 화면 | 가상 사례 9건의 후속 검토, 알림 후보, 동의, 조건 일치와 시험 발송을 구분. 실제 수요로 표시하지 않음 |
| F10 | 관심 메뉴 알림 | 사용자가 관심 조건을 직접 선택하고 브라우저 알림에 동의. 해제 가능. 같은 시험 이벤트 중복 요청 차단 |

설명에 사전 밖 요구가 남아도 필터가 이를 보장하지는 않습니다. 당류, 카페인, 알레르기 등은 현재 추천의 충족 조건으로 사용하지 않습니다.

## 5. 데이터

추천 목록: 딸기 딜라이트 요거트 블렌디드, 망고 패션 프루트 블렌디드, 초콜릿 크림 칩 프라푸치노, 카페 라떼, 바닐라 크림 콜드 브루.

각 후보는 출처, 확인일, 판매 범위, 특징 분류 이유를 가집니다. 공식 설명과 설계자가 해석한 감각 분류를 구분합니다.
목록에 있다는 사실은 특정 지점의 판매나 재고를 뜻하지 않습니다. 자료 확인일이 30일을 넘으면 서버 추천에서 제외합니다. 조회 실패를 단종으로 바꾸지 않습니다.
메뉴 이력 조사 6종과 추천 5종은 다른 자료입니다. 지역 확대 이력을 현재 판매 지점 목록으로 쓰지 않습니다.

## 6. 남은 요구의 활용 기준

현재 사용자 기록은 기기 안에만 저장하며 중앙 수집하지 않습니다.
알림을 신청하면 요구 문장 원문이 아니라 무작위 기기 식별값의 해시와 사용자가 직접 고른 관심 조건만 로컬 시험 서버에 저장합니다. 가입, 이메일과 전화번호는 받지 않습니다.
운영 검토 보조 규칙은 수집 동의 없음, 변경 이유 모름, 해석 검토, 사전 밖 요구, 목록 누락, 검토 대기, 현재 목록에서 미충족, 대안 있음, 안전 조건의 9가지입니다.
사람이 확인한 조건을 입력받습니다. 자유 문장만으로 불만 원인을 자동 확정하지 않습니다.
목록 누락이면 데이터 보완, 해석 오류이면 평가 문장 보완, 확인 후에도 미충족이면 인터뷰나 시음 검토로 연결합니다.

## 7. 운영과 개인정보

- Gemini 비밀 키는 서버에서만 사용하며 저장소에 올리지 않음.
- 고객 문장 전송 전에 동의를 받고 민감정보 입력을 안내/차단.
- AI 운영 기록에는 원문 대신 상태와 처리 시간, 사용량 등 저장.
- 하루 호출 한도 40회. 실패 시 무제한 자동 재시도 없음.
- 정기 점검 일정과 실제 완료 기록을 구분. 수동 실행을 예약 실행 실적으로 적지 않음.
- 서버는 로컬 실행용. 외부 공개 운영, 접근 통제 강화와 개인정보 운영 절차는 별도 과제.
- 브라우저 알림 권한은 사용자가 직접 허용. 동의 해제 뒤에는 관심 조건을 비활성화.
- 시험 이벤트는 가상 자료이며 실제 스타벅스 출시 소식으로 발송하지 않음. 실제 원격 푸시 제공자 연결은 별도 과제.

## 9. 후속 결정 기준

1. 연결이 가능한 환경에서 같은 평가 기준으로 개발 문장을 실행. 오류 유형을 확인한 뒤 수정하고 분리 문장으로 확인.
2. 실패한 호출은 연결 신뢰성에 포함하고, 의미 정확도는 응답을 받은 문장 기준으로 별도 표시. 미실행은 분모에서 제외.
3. 외부 이용자 시험에서는 같은 과업의 완료 시간, 조건 누락, 수정 이유를 비교. 입력과 읽기 시간도 포함.
4. AI 방식이 도움이 되지 않거나 오류 수정 부담이 크면 직접 선택을 기본으로 유지/전환.
5. 데이터 범위를 넓힐 때는 메뉴 수보다 공식 출처와 분류 기준을 먼저 검토.

## 10. 이번에 만들지 않는 것

회원가입, 공개 커뮤니티/투표, 주문/결제, 스타벅스 제출, 제조 가능한 레시피 자동 개발, 매출/수요 예측, 특정 지점 실시간 재고, 이메일/문자와 실제 원격 푸시 운영.
과거 서버 모듈은 보존하지만 고객 화면에서 사용하지 않습니다. 서비스 목적과 무관한 기능 확장은 하지 않습니다.
