# 프로젝트 목적과 직무 관련 경험

## 만든 서비스

좋아했던 음료의 맛과 질감을 바탕으로 지금 마실 후보를 비교합니다. 필수 조건에 맞는 후보가 없으면 추천을 보류하고, 찾지 못한 특징과 고객이 동의한 관심 주제를 연결합니다. 이후 관련 소식이 생겼을 때만 다시 알려주는 CRM형 AI 서비스입니다.

PDF에는 기획과 화면을, Excel에는 시험 결과를 담았습니다. GitHub에서 코드를 실행하고 원자료를 확인할 수 있습니다.
본인의 실제 경험에서 문제를 정의하고, 공개 자료 조사와 가상 사용자 시나리오 시험으로 추천 조건 및 실패 대응을 검증했습니다. 외부 이용자 대상 사용성 검증은 후속 과제로 남겼습니다.

## 남은 요구를 어떻게 활용하나요?

입력 문장과 상세 요구는 기기 안에만 저장됩니다. 알림을 신청할 때는 무작위 기기 식별자의 해시값과 고객이 직접 고른 관심 주제만 로컬 서버에 저장합니다. 9개의 가상 시나리오로 운영 판단 흐름을 시험했으며 실제 고객 자료는 사용하지 않았습니다.

| 관찰 | 해석하기 전 확인 | 다음 행동 | 이번 상태 |
|---|---|---|---|
| 서비스 목록에 없는 메뉴가 실제로 있음 | 공식 설명/확인일/판매 범위 | 데이터 담당이 검증 후 목록 보완 | 과일/요거트 2종 보완 |
| 사용자가 AI 해석을 바꿈 | 오해석인지 취향 변경인지 | 동의받은 수정 이유를 AI 시험에 반영 | 수정 반영 동작 확인, 오류 통계 없음 |
| 확인 조건에 후보 없음 | 현재 목록 범위가 충분한지 | 기획 담당이 인터뷰나 시음으로 확인 | 쌀 필수 보류 확인, 신메뉴 수요 확정 아님 |
| 같은 관심 주제에 공식 소식이 생김 | 동의 상태, 주제 일치, 중복 여부 | 조건이 모두 맞을 때만 한 번 알림 | 가상 이벤트 1건으로 중복 차단 확인 |

대시보드의 숫자는 가상 시나리오와 로컬 시험 기록입니다. 고객 수요나 출시 성과로 해석하지 않으며 요청 건수만으로 신메뉴를 만들거나 출시량을 정하지 않습니다.
후속 검증에서는 같은 조건의 대안 선택 이유와 실제 시음 차이를 보고 인터뷰 질문을 바꿉니다.

## 공고의 주요 업무와 비교

| 업무 | 이 프로젝트가 보여주는 것 | 주장하지 않는 것 |
|---|---|---|
| 데이터/AI 전략 | 단일 서비스의 문제, 데이터, AI 역할과 위험 설정 | 전사 전략 수립 경험 |
| AI Agent 구축/운영 | Gemini 연결, 조건 검사, 실패 처리, 호출 기록 | 자율 주문 Agent, 장기 실서비스 운영 |
| 고객 분석 | 본인 경험과 공개 자료의 근거/한계 구분, 남은 요구를 쌀/식감/음료 형태/취지로 분류 | 대표 고객 표본이나 수요 규모 |
| 의사결정 지원 | 목록 누락과 해석 오류를 구분하고, 동의/주제 일치/중복 차단을 대시보드에서 확인 | 자동 신메뉴 출시 판단 |
| 매출/수요 예측, 매장 분석 | 프로젝트 밖으로 명시 | 가상 숫자로 실제 예측 성과 표현 |

## 검토와 인수인계를 위해 남긴 자료

1. 사실과 해석 구분: 공식 설명, 감각 분류 이유, 확인일을 함께 저장.
2. 실패 공개: 이전 H04 두 차례 실패, 현재 R03 검사기 실패와 재실행 보존.
3. 인수인계: 직접 선택으로 보는 무료 데모, 재실행 방법, 현재/과거 자료 구분.

저는 문제와 기능 범위를 정하고 결과를 검토했습니다. 조사 보조와 코드 작성/시험에는 Codex를 사용했고, 서비스의 취향 해석에는 Gemini를 연결했습니다.
