# 선택 이유, 오류 분석, 장애 대응

## 무엇을 확인하려 했나

기억에서 좋아했던 특징을 정리하고, 이번 선택에서 필요한 조건을 확인한 뒤 후보를 비교하는 서비스를 만들었습니다.
가상 입력으로 확인할 대상은 조건 추출, 잘못된 응답 차단, 질문 표시, 실패 후 복구입니다.
고객이 더 쉽게 골랐는지, 맛이 만족스러웠는지, 구매로 이어졌는지는 별도 사용자 시험이 필요합니다.

## 본인의 선택 과정을 나눠 본 이유

| 단계 | 본인이 말한 경험 | 설계에 반영한 판단 |
|---|---|---|
| 좋아했던 이유 | 쌀의 구수함, 프라푸치노, 과자 같은 토핑, 출시 취지 | 맛과 질감 외의 이유도 남겨야 함 |
| 대안을 알게 된 계기 | 당시 추천을 받아 딸기 요거트 음료를 시도 | 원래 맛과의 유사성만으로 선택을 설명할 수 없음 |
| 받아들인 이유 | 시원하게 갈린 음료를 좋아했고 맛도 괜찮았음 | 좋아했던 특징 모두가 다음 잔의 필수 조건인 것은 아닐 수 있음 |
| 아직 모르는 것 | 가격, 구매 장소, 반복 구매, 다른 후보를 거절한 이유 | 기억나지 않는 부분을 임의로 채우지 않음 |

한 사람의 회고입니다. 이 서비스의 추천 결과나 전체 고객의 성향으로 일반화하지 않습니다.
출시 취지를 좋아했다는 말을 쌀 맛 선호로 변환하지 않도록 평가 문장에 넣었습니다.

## 어려운 표현의 평가 기준

[시험 문장 16개](../evidence/hard-cases.json)를 먼저 정했습니다. 개발용 8개와 분리 평가용 8개입니다.
두 묶음 모두 같은 작성자가 설계했으므로 독립적인 외부 평가가 아닙니다.
분리 평가용은 수정 완료 뒤 실행하고, 결과를 보고 그 묶음에 맞춰 다시 수정하지 않는 계획입니다.

| 표현 | 확인할 기준 |
|---|---|
| 과거에는 좋았지만 지금은 피함 | 현재 명시적 의사 우선 |
| 없어도 괜찮음 | 허용을 선호로 만들지 않음 |
| 커피 맛은 싫지만 향은 좋음 | 현재 특징 사전으로 구분하기 어려우면 질문 |
| 지역 농가 상생 취지가 좋음 | 맛으로 바꾸지 않고 설명에 보존 |
| 갈린 질감은 좋지만 얼음 덩어리는 싫음 | 질감 전체를 싫어한다고 단정하지 않음 |
| 입력 안에 모델 실행 지시가 섞임 | 실행 지시를 취향 근거로 사용하지 않음 |
| 애매한 부정과 모순 | 필수 여부를 추측하지 않고 확인 |
| 당도, 카페인, 알레르기 | 사전 밖 요구를 버리지 않으며 안전을 보장하지 않음 |

평가 항목은 선호, 비선호, 쌀 필수 여부, 확인 질문, 사전 밖 요구 보존입니다.
정답은 이 프로젝트의 설계 기준이며 유일한 언어 해석이라고 주장하지 않습니다.

### 실행 결과와 중단 판단

이번 실제 연결 시도에서 D01~D04는 UPSTREAM 2회와 TIMEOUT 2회로 답변을 받지 못했습니다.
D05 진행 중 중단했으며 제공자 수신과 과금 여부는 확인하지 못했습니다.
별도 단순 입력 연결 점검 1회도 TIMEOUT이었습니다.
분리 평가 8개와 해석 개선 전후 비교는 실행하지 않았습니다. 의미 정확도와 개선율은 미산출입니다.

[실행 원본](../evidence/hard-baseline.json)과 [중단/추가 점검 기록](../evidence/hard-execution-status.json)을 분리했습니다.
실패를 성공으로 바꾸거나 정상 응답을 가짜로 채우지 않았습니다.
평가 실행기는 전송 시작부터 기록하고, 연속 연결 실패 2회에서 중단하도록 보완했습니다.
연결 실패율은 평가 환경에서 관찰한 값이며 Gemini 전체 장애를 뜻하지 않습니다.

### 실제로 발견한 오류

기존 3종 목록의 24회 해석 시험에서는 H04의 쌀 선호 추출이 2회 빠졌습니다.
이는 이번 16문장 결과가 아닙니다. [당시 원본](../evidence/taste-evaluation.json)을 유지했습니다.
필수 쌀 조건은 잡혔기 때문에 후보 결과만 보면 오류를 놓칠 수 있습니다.
따라서 최종 후보와 선호/비선호/필수 조건을 따로 검사하도록 평가 기준을 구성했습니다.

형식 검사에는 다른 한계도 있습니다. '바닐라 향이 좋아요'라는 실제 인용을 붙이고 coffee 태그를 반환하면 원문 존재 검사는 통과할 수 있습니다.
이를 자동 시험으로 확인했습니다. 인용 검사를 의미 정확도의 증거로 사용하지 않고 사용자 확인을 유지했습니다.

## 확인 질문이 사라지는 문제를 재현하고 수정

왜: AI가 확정할 수 없는 조건은 사용자가 확인해야 합니다.
문제: 응답의 question 필드는 검사했지만 화면에서는 understanding만 표시했습니다.
재현: 고정한 가상 응답에 확인 질문을 넣어 화면 시험을 실행했습니다. 질문 표시 검사만 실패했습니다.
수정: 질문을 기존 취향 확인 설명에 표시했습니다. 디자인이나 처리 단계를 늘리지는 않았습니다.
결과: 같은 장애/복구 시험 8항목에서 수정 전 7개, 수정 후 8개를 확인했습니다.
이 수치는 모델 정확도나 고객 성공률이 아닙니다.

## 남은 요구를 구분하는 기준

[분류 코드](../app/need-triage.cjs)는 운영 검토용이며 고객 화면에 자동 분류 결과를 표시하지 않습니다.
입력 원문만으로 원인을 확정하지 않고 사람이 확인한 조건을 받습니다.
실제 기록의 중앙 수집이나 집계는 연결하지 않았습니다.

| 분류 | 먼저 확인할 것 | 다음 행동 |
|---|---|---|
| 수집 동의 없음 | 기록 활용 동의 | 집계하지 않음 |
| 변경 이유 모름 | 생각 변화인지 AI 오해석인지 | 사용자에게 이유 확인 |
| 해석 검토 | 원문과 수정 내용 대조 | 평가 문장에 반영 |
| 사전 밖 요구 | 상생, 당도 등 현재 표현 못 하는 조건 | 별도 조사, 맛으로 치환 금지 |
| 목록 누락 | 공식 출처에서 다른 후보 확인 | 목록 보완 |
| 검토 대기 | 필수 조건과 목록을 확인했는지 | 확인 전 수요 판단 보류 |
| 현재 목록에서 미충족 | 조건과 목록 확인 후에도 후보 없음 | 인터뷰나 시음 검토, 시장 부재로 단정 금지 |
| 대안 있음 | 실제 선택 여부와 이유 | 후보 표시를 구매로 세지 않음 |
| 안전 조건 | 알레르기 등 보장할 수 없는 요구 | 공식 정보 확인 안내, 안전한 음료라고 추천하지 않음 |

[가상 분류 사례 9개](../evidence/need-triage-cases.json)를 자동 검사했습니다.
분류 결과가 신메뉴 출시나 판매량 결정으로 바로 이어지지는 않습니다.

## 장애 대응 시험

외부 응답이 오지 않도록 가상 전송 계층을 넣었습니다. 실제 외부 서비스에 장애를 일으키지 않았습니다.
시험 제한은 150ms, 실제 서비스의 취향 해석 제한은 12초입니다. 빠르게 검사하기 위한 설정이며 실제 복구 시간으로 해석하지 않습니다.

1. 서버가 시간 초과를 TIMEOUT으로 기록
2. 화면에서 오류 안내, 입력 원문 보존, 버튼 재사용
3. 직접 조건을 선택해 후보 비교
4. 가상 응답을 정상으로 바꾸고 다시 요청
5. 확인 질문과 성공 기록 확인

[수정 전 기록](../evidence/recovery-before.json), [수정 후 기록](../evidence/recovery-after.json), [수정 후 화면](../evidence/recovery-after.png)을 남겼습니다.
첫 검사기는 결과 화면에 없는 시작 버튼을 찾아 중단했습니다. 검사 경로를 바로잡은 뒤 위 기록을 생성했습니다.
가상 연결의 복구이며 실제 Gemini 연결 복구나 장기 운영 안정성을 증명하지 않습니다.

## 이 자료로 설명할 수 있는 역량

- 기획: 선호와 필수 조건을 나누고, AI가 처리하지 못하는 요구의 다음 확인 방법을 정함
- 개발: 평가 기준을 먼저 적고, 모델 해석과 코드/UI 실패를 구분하며 재현 가능한 검사를 작성
- 고객 분석: 실제 경험, 설계 가설, 가상 입력, 미측정 고객 효과를 구분
- 운영: 장애를 기록하고 불필요한 재시도를 멈추며 직접 선택으로 이어지는 경로를 시험

아직 설명할 수 없는 것은 고객 만족도 향상, 매출 효과, 신메뉴 수요 규모, 실제 장기 운영 성과입니다.
